# 검증 전략

## 원칙

검증은 많이 만드는 것이 목적이 아니라, 실제 회귀 위험이 높은 경계를 짧게
재현하는 것이 목적이다. 구현 중에는 가장 가까운 검증을 실행하고, 큰 phase나
배포 직전에만 전체 gate를 한 번 실행한다.

## 계층별 검증

| 계층 | 도구 | 확인 대상 |
| --- | --- | --- |
| 단위 | JUnit/Vitest | 상태 전이, validation, mapper, 순수 규칙 |
| 웹 MVC | Spring Boot test | controller 계약, status, security 경계 |
| 통합 | Testcontainers PostgreSQL | migration, transaction, constraint, query |
| 구조 | Modulith/ArchUnit | module 의존과 package 규칙 |
| frontend | typecheck/Vitest | API client, component 상태, pagination |
| E2E | Playwright | 핵심 로그인·게시·검색·신고 흐름 |
| smoke | shell script | frontend-backend 연결과 health |
| 성능 | k6·performanceTest | 공개 feed, read/write 혼합, contention |

## 권장 순서

```bash
# 코드 변경 중
./gradlew test --tests 'com.townpet....관련테스트'

# backend phase 완료
./gradlew clean check migrationTest

# frontend phase 완료
(cd frontend && corepack pnpm typecheck && corepack pnpm test && corepack pnpm build)

# API와 화면을 함께 바꾼 경우
./scripts/frontend-backend-smoke.sh
```

실행하지 않은 Docker·SMTP·VPS·백업 결과를 로컬 테스트 통과로 대체하지 않는다.
성능 수치는 workload, 데이터 크기, CPU, DB cache, concurrency를 함께 기록하고
운영 SLA로 확대 해석하지 않는다.

## 실패를 읽는 법

- migration 실패: 현재 DB schema version과 Flyway history를 먼저 확인한다.
- security test 실패: authentication과 ownership을 구분해 request principal을 확인한다.
- Modulith 실패: 다른 module 내부 타입을 직접 참조했는지 확인한다.
- E2E 실패: frontend API base URL, CSRF, session cookie, fixture 순서를 확인한다.
- Testcontainers 실패: Docker resource와 port를 확인하고 무작정 parallelism을 늘리지 않는다.
