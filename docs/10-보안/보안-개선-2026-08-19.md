# 보안 개선 — 2026-08-19

## 대상

초기 보안 점검에서 출시 차단으로 판정한 다음 두 항목을 구현했다.

1. presigned upload의 사용자별 quota·횟수 제한·Content-Length 제한
2. password reset/email verification의 IP·전역 Rate Limit

코드·설정·frontend client·backend 테스트를 변경했으며, 실제 운영 VPS와 MinIO 환경에는 아직 배포하지 않았다.

## 1. 업로드 abuse 방어

### 적용 내용

- `src/main/java/com/townpet/media/MediaService.java`
  - 사용자별 UTC 날짜 기준 업로드 생성 횟수를 50회로 제한
  - 사용자별 누적 object 저장량을 100 MiB로 제한
  - `member_account` row를 `FOR UPDATE`로 잠근 뒤 quota를 계산해 동시 create 요청의 우회를 방지
  - `UPLOADING`, `READY`, `ATTACHED` 등 `ABANDONED`가 아닌 asset의 byte size를 저장 quota에 반영
- `src/main/java/com/townpet/media/MediaController.java`
  - quota 초과 시 `429 Too Many Requests` 반환
  - upload grant는 `UPLOADING` 상태에서만 반환하고, finalize 이후에는 빈 grant를 반환
- `src/main/java/com/townpet/media/MinioObjectStorage.java`
  - 기존 presigned PUT을 MinIO `PostPolicy` 기반 presigned POST로 변경
  - `key`와 `Content-Type`을 exact condition으로 서명
  - `content-length-range`를 선언된 `byteSize` 하나의 값으로 제한
  - presigned POST 만료시간은 asset 만료시간과 설정된 presign expiry 중 더 짧은 값 사용
- `src/main/java/com/townpet/media/ObjectStoragePort.java`
  - upload URL과 form fields를 분리하는 storage adapter 계약 추가
- `frontend/src/api/client.ts`
  - production presigned POST의 form fields를 `FormData`로 전송
  - local/test adapter의 기존 PUT fallback 유지

### 적용된 정책

| 정책 | 값 | 적용 위치 |
|---|---:|---|
| 사용자별 UTC 일일 upload create 횟수 | 50회 | `MediaService.MAX_UPLOADS_PER_UTC_DAY` |
| 사용자별 누적 object 저장량 | 100 MiB | `MediaService.MAX_STORED_BYTES_PER_MEMBER` |
| 파일 단일 크기 | 10 MiB | 기존 backend validation 및 multipart 설정 |
| presigned upload content length | metadata `byteSize`와 정확히 일치 | MinIO `PostPolicy` |
| upload grant 만료 | asset expiry와 `presign-expiry-seconds` 중 짧은 값 | `MinioObjectStorage` |

quota는 별도 counter table이 아니라 기존 `upload_asset` 원장을 사용한다. owner row lock 아래에서 count/sum을 조회하므로 같은 사용자의 동시 요청은 직렬화된다. 만료된 `UPLOADING` asset이 정리되면 해당 예약 byte도 quota 계산에서 사라진다.

## 2. password reset/email verification abuse 방어

### 적용 내용

- `src/main/java/com/townpet/identity/PasswordResetController.java`
  - password reset request에 IP별 분당 30회 제한
  - password reset request에 전역 분당 300회 제한
- `src/main/java/com/townpet/identity/EmailVerificationController.java`
  - email verification request에 IP별 분당 30회 제한
  - email verification request에 전역 분당 300회 제한
- 기존 service-level 계정별 시간당 3회 제한은 유지
- 제한 초과 시 기존 `RequestRateLimiter`가 `429 Too Many Requests`를 반환
- 응답은 기존과 같이 계정 존재 여부를 드러내지 않는 generic `202 Accepted` 흐름을 유지

현재 `RequestRateLimiter`는 단일 JVM 메모리 기반이다. 현재 단일 backend 컨테이너 운영에는 적용되지만, 다중 인스턴스 운영 전에는 shared store 또는 edge/WAF rate limit으로 확장해야 한다.

## 3. 검증 결과

### 통과

- `./gradlew compileJava compileTestJava`: PASS
- `./gradlew test --tests com.townpet.identity.IdentityMemberControllerTest --tests com.townpet.identity.AccountTokenDeliveryUnavailableTest --tests com.townpet.common.RequestRateLimiterTest`: PASS
- `cd frontend && corepack pnpm typecheck`: PASS
- `cd frontend && corepack pnpm build`: PASS
- 변경 Java 파일에는 Spotless 위반이 없음. 전체 `spotlessJavaCheck`는 이번 변경과 무관한 기존 작업 트리 파일의 format violation으로 실패

### 제한 사항

- `MediaControllerTest`는 Testcontainers PostgreSQL을 필요로 하며, 이번 실행 환경에는 Docker daemon이 없어 initialization 단계에서 실행되지 않았다.
- 따라서 quota의 실제 PostgreSQL row lock·동시 요청 동작과 MinIO presigned POST의 실제 browser/CORS upload는 아직 실행 증거가 없다.
- 배포 전 Docker/MinIO 환경에서 다음을 추가 검증해야 한다.
  1. 같은 member의 51번째 create가 `429`가 되는지
  2. 서로 다른 member의 quota가 독립적인지
  3. 동시 create 요청이 quota를 초과하지 않는지
  4. 잘못된 Content-Length의 presigned POST가 MinIO에서 거부되는지
  5. finalize 이후 새 upload grant가 발급되지 않는지
  6. reset/verification 요청의 IP별·전역 limit이 실제 `429`를 반환하는지
