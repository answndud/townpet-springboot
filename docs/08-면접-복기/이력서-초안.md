## 프로젝트

### TownPet Spring Boot | 반려동물 커뮤니티 플랫폼

2026 · 개인 프로젝트 · 설계/개발/검증/배포 전 과정

[GitHub](https://github.com/answndud/townpet-springboot) · [실행 서비스](https://townpet.cloud)

기존 TownPet의 화면, URL, 주요 사용 흐름을 유지하면서 JavaScript 기반 백엔드를 Java/Spring Boot로 재작성했습니다. 게시글·댓글·좋아요·북마크·알림·신고·입양·봉사·돌봄·미디어 기능을 React/Vite와 연결했고, 권한·트랜잭션·동시성·조회 성능·복구 경계를 다시 설계했습니다.

**사용 기술**  Java, Spring Boot, Spring Security, Spring Modulith, PostgreSQL/PostGIS, Flyway, JPA, React/Vite, Docker Compose, MinIO

**문제와 해결**

- **인증·권한:** URL에 포함된 member ID를 그대로 믿으면 다른 사용자의 리소스를 조작할 수 있었습니다. 인증된 세션 사용자와 리소스 소유자를 함께 확인하고, 운영자 기능은 deny-by-default RBAC와 CSRF로 분리했습니다.
- **피드 조회:** offset 방식은 글이 새로 추가되거나 삭제될 때 중복과 누락이 생길 수 있었습니다. `EXPLAIN (ANALYZE, BUFFERS)`에서 offset이 커질수록 불필요한 row scan이 늘어나는 것을 확인한 뒤, `(created_at, id)` 복합 인덱스와 keyset cursor를 API, DB, 프론트엔드에 동일하게 적용했습니다.
- **동시성:** 조회수를 `find → save`로 저장하면 lost update가 생길 수 있고, 봉사 수용은 모집 정원을, 미디어 첨부는 허용 개수 한도를 초과할 수 있었습니다. 조회수는 `ON CONFLICT DO UPDATE ... RETURNING` atomic upsert로 바꾸고, 공유 불변식이 있는 변경에만 row lock을 적용했습니다.
- **후속 처리:** 알림 발송을 핵심 트랜잭션과 분리하기 위해 Event Publication Registry와 PostgreSQL을 사용했습니다. 재시도로 다시 실행되어도 중복 처리되지 않도록 consumer를 구성했습니다.

**검증 결과**

- 로컬 Docker/PostgreSQL의 100,000건 fixture에서 public feed p95 `67.13ms → 5.01ms`, 처리량 `19.40 → 420.78 req/s`를 확인했고, 최근 3회 반복 실행에서 p95 `4.35~6.40ms`, 오류 0을 기록했습니다.
- 조회수 증가 요청 160건을 8개 thread로 동시 실행해 요청 수와 최종 counter를 대사했습니다.
- 정원 경합 상황에서 정원 불변식이 깨지지 않는 것을 동시성 테스트로 검증했습니다.
- `EXPLAIN (ANALYZE, BUFFERS)`와 재현 가능한 테스트 데이터로 인덱스, 정렬, 목록 상한을 검증했습니다.
- 두 프로젝트의 PostgreSQL·MySQL·MinIO 백업·복구와 age 암호화/복호화, 컨테이너 이미지 롤백 리허설을 수행했습니다.

**기술 선택**

Redis와 Kafka는 처음부터 넣지 않았습니다. 쿼리 실행 계획, DB 경합, 이벤트 적체를 먼저 측정했고, 100,000건 피드와 30분 안정성 테스트에서 분산 캐시나 메시지 브로커가 해결할 병목을 확인하지 못했습니다. 필요 이상의 복잡도를 추가하지 않고 현재 구조를 유지했습니다.

**배포 경험**

관리형 호스팅에 애플리케이션만 올리는 수준에서 끝내지 않고, netcup VPS의 OS, Docker Compose, 데이터 볼륨, 네트워크를 직접 구성했습니다. Cloudflare는 DNS와 도메인 연결에 사용하고, Caddy는 하나의 80/443 진입점에서 호스트명으로 두 프로젝트를 분기합니다. GitHub Actions가 GHCR 이미지를 빌드하면 VPS에서는 다시 빌드하지 않고 pull·restart만 수행합니다. 단일 VPS의 장애가 두 서비스에 함께 영향을 주는 한계는 암호화 백업과 복구 리허설로 보완했습니다.

### KinderP | 유치원 다중 테넌트 운영 플랫폼

2026 · 개인 프로젝트 · 설계/개발/검증/배포 전 과정

[GitHub](https://github.com/answndud/kinderp) · [실행 서비스](https://kinderp.cloud)

원장, 교사, 학부모가 사용하는 내부 운영 플랫폼입니다. TownPet에서 적용한 권한, 상태 전이, 실패 복구 원칙을 다중 테넌트 업무에 다시 적용했습니다.

**사용 기술**  Java, Spring Boot, Spring Security, MySQL, Redis, JPA, Flyway, Docker Compose, Caddy, GitHub Actions

**문제와 해결**

- **다중 테넌트 권한:** 역할만 확인하면 다른 유치원의 데이터에 접근할 수 있었습니다. 회원 역할과 유치원 소유권을 함께 확인하는 접근 정책을 구현했습니다.
- **업무 상태 전이:** 입학 신청의 신청·승인·제안·수락·거절·대기열 상태와 출결 변경 요청의 허용 전이를 명시하고 검사 기록을 남겼습니다.
- **데이터 정합성:** 출결, 인수인계, 입학 처리를 트랜잭션으로 묶어 동시 요청이 상태를 덮어쓰지 않도록 했습니다.
- **알림 전송 실패:** 알림을 Outbox와 전송 상태로 분리하고, 재시도·실패 상태·운영자 조회 경로를 구성했습니다.
- **운영 안정성:** refresh rotation, rate limit, 인증 감사 로그, Testcontainers 기반 MySQL/Redis 검증, Docker health check와 GHCR image rollback을 구성했습니다.
