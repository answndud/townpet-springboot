## 프로젝트

### TownPet Spring Boot | 반려동물 커뮤니티 플랫폼

2026 · 개인 프로젝트 · 설계/개발/검증/배포 전 과정

[GitHub](https://github.com/answndud/townpet-springboot) · [실행 서비스](https://townpet.cloud)

기존 TownPet의 화면·URL·주요 사용자 여정을 보존하면서 JavaScript 기반 backend를 Java/Spring Boot로 재설계했습니다. 단순 기능 이식이 아니라 권한·트랜잭션·동시성·조회 성능·복구 경계를 다시 정의한 **운영 가능한 재작성 프로젝트**입니다.

**사용 기술**  Java, Spring Boot, Spring Security, Spring Modulith, PostgreSQL/PostGIS, Flyway, JPA, React/Vite, Docker Compose, MinIO

**담당 업무와 문제 해결**

- **인증·권한:** URL의 member ID를 믿는 방식은 다른 사용자의 리소스 조작으로 이어질 수 있었습니다. session principal과 resource ownership을 application service에서 함께 검사하고, 운영자 영역은 deny-by-default RBAC·CSRF로 분리했습니다.
- **피드 pagination:** offset 방식은 데이터 삽입 중 중복·누락이 생기고 뒤 페이지에서 불필요한 row를 건너뛰었습니다. `(created_at, id)` 복합 index와 keyset cursor를 API·DB·frontend에 동일한 계약으로 적용했습니다.
- **대량 변경:** 게시글 공개범위 변경이 entity 전체를 읽고 `saveAll`하는 구조였습니다. 조건부 PostgreSQL bulk update로 바꾸고 실제 변경 row만 version·updatedAt을 갱신했습니다.
- **동시성:** 조회수 `find → save`의 lost update와 봉사 수용·미디어 첨부의 capacity 초과 가능성을 확인했습니다. 조회수는 `ON CONFLICT DO UPDATE ... RETURNING` atomic upsert로 바꾸고, 공유 불변식이 있는 mutation에만 row lock을 적용했습니다.
- **후속 처리:** 알림 전송을 핵심 transaction에서 분리하기 위해 Event Publication Registry와 PostgreSQL을 사용하고, 재시도 가능한 consumer를 idempotent하게 구성했습니다.

**검증 결과**

- 동일한 local Docker/PostgreSQL fixture 100,000건에서 public feed p95 `67.13ms → 5.01ms`, 처리량 `19.40 → 420.78 req/s`
- public feed 최신 3회 측정 p95 `4.35~6.40ms`, 오류 0
- 조회수 160개 동시 요청을 8개 thread로 실행해 최종 counter와 요청 수 대사
- capacity contention에서 정원 불변식 유지, application p95 약 `238.98ms` 기록
- `EXPLAIN (ANALYZE, BUFFERS)`·deterministic fixture로 index·정렬·목록 상한 검증
- PostgreSQL·MinIO·MySQL 백업/복구, age 암호화/복호화, 이미지 rollback rehearsal 수행

**선택의 근거**

Redis·Kafka를 도입하고 성능이 좋아졌다고 가정하지 않았습니다. query plan·DB contention·event backlog를 먼저 측정했고, 100,000건 피드와 30분 soak에서 해결할 병목이 확인되지 않아 도입을 보류했습니다. 이는 기술의 개수보다 **복잡도를 감당할 근거**를 중시한 선택입니다.

### KinderP | 유치원 다중 테넌트 운영 플랫폼

2026 · 개인 프로젝트 · 설계/개발/검증/배포 전 과정

[GitHub](https://github.com/answndud/kinderp) · [실행 서비스](https://kinderp.cloud)

원장·교사·학부모가 사용하는 내부 운영 플랫폼입니다. TownPet에서 확립한 “actor·소유권·상태 전이·실패 복구” 원칙을 다중 테넌트 업무 도메인에 다시 적용해, 한 프로젝트의 우연한 해결이 아닌 **재현 가능한 backend 설계 역량**을 검증했습니다.

**사용 기술**  Java, Spring Boot, Spring Security, MySQL, Redis, JPA, Flyway, Docker Compose, Caddy, GitHub Actions

**담당 업무와 문제 해결**

- **다중 테넌트 권한:** 역할만 검사하면 다른 유치원의 데이터에 접근할 수 있었습니다. member role과 kindergarten ownership을 함께 검사하는 access policy를 구현했습니다.
- **업무 상태 전이:** 입학 신청의 신청·승인·제안·수락·거절·대기열 상태와 출결 변경 요청의 actor·허용 전이를 명시하고 audit log로 남겼습니다.
- **데이터 정합성:** 출결·인수인계·입학 처리를 transaction으로 묶어 두 요청이 서로의 상태를 덮어쓰지 않도록 했습니다.
- **알림 실패:** 알림을 Outbox와 delivery status로 분리하고 retry·dead-letter·운영자 조회 경로를 구현했습니다.
- **운영 안정성:** refresh rotation·rate limit·auth audit log, Testcontainers 기반 MySQL/Redis 검증, Docker health check와 GHCR image rollback을 구성했습니다.
- **공동 배포:** TownPet과 하나의 netcup VPS에서 80/443 포트 충돌이 없도록 공용 Caddy·`edge` network·내부 service 포트를 분리했습니다.
