## 대표 프로젝트 1 — TownPet Spring Boot

### 반려동물 커뮤니티 플랫폼 재작성

2026 · 개인 프로젝트 · 설계/개발/검증/배포 · [GitHub](https://github.com/answndud/townpet-springboot) · [서비스](https://townpet.cloud)

기존 TownPet의 화면과 사용자 경험을 유지하면서 backend를 Java/Spring Boot modular monolith로 재작성했습니다. 게시글·댓글·좋아요·북마크·알림·신고·입양·봉사·돌봄·미디어 업로드를 React/Vite frontend와 연결했습니다.

### 문제와 해결

- **권한 경계:** URL의 member ID나 client 입력을 권한 근거로 사용하면 다른 사용자의 게시글·댓글·미디어를 조작할 수 있었습니다. Spring Security principal과 resource ownership을 application service에서 함께 검사하고, 운영자 권한은 deny-by-default RBAC로 분리했습니다.
- **피드 일관성:** offset pagination은 데이터 삽입 중 페이지가 흔들리고 뒤 페이지에서 불필요한 row를 건너뛰었습니다. `(created_at, id)` 복합 정렬과 keyset cursor를 API·DB index·React client에 같은 계약으로 적용했습니다.
- **대량 변경 비용:** 작성자 게시글 공개범위 변경이 entity 전체 로딩과 `saveAll`에 의존했습니다. 조건부 PostgreSQL bulk update로 바꾸고, 실제 상태가 바뀐 row만 version·updatedAt을 갱신했습니다.
- **동시성 정합성:** 조회수는 `find → save` 경쟁으로 lost update가 가능했고, 봉사 수용·미디어 첨부는 동시에 정원·개수 불변식을 넘을 수 있었습니다. 조회수는 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` atomic upsert로, 공유 자원 변경은 필요한 경우에만 row lock으로 변경했습니다.
- **후속 처리:** 알림 전송을 요청 transaction에 묶으면 외부 전송 지연과 재시도 때문에 핵심 요청이 불안정해집니다. Spring Modulith Event Publication Registry와 PostgreSQL을 사용해 후속 이벤트를 분리하고 consumer를 idempotent하게 만들었습니다.

### 검증 결과

- 동일한 local Docker/PostgreSQL fixture의 publication 100,000건에서 public feed p95 `67.13ms → 5.01ms`를 측정했습니다.
- public feed 최신 3회 측정은 p95 `4.35~6.40ms`, 오류 0이었습니다.
- 조회수 동시 요청 160건을 8개 thread로 실행해 요청 수와 최종 counter를 대사했습니다.
- capacity contention에서 정원 불변식을 지켰고, row lock 비용은 application p95 약 `238.98ms`로 분리 기록했습니다.
- `EXPLAIN (ANALYZE, BUFFERS)`와 deterministic fixture로 index·정렬·목록 상한 query를 검증했습니다.
- PostgreSQL·MinIO paired backup, checksum, disposable restore, age 암호화·복호화와 이미지 rollback rehearsal을 수행했습니다.

### 기술적 판단

Redis·Kafka를 처음부터 넣지 않았습니다. query plan·DB contention·event backlog를 먼저 측정하고, 현재 병목이나 eventual consistency 요구가 없다는 근거를 확인한 뒤 cache invalidation·consumer lag·운영 복잡도를 추가하는 도입은 보류했습니다.

## 대표 프로젝트 2 — KinderP

### 유치원 다중 테넌트 운영 플랫폼

2026 · 개인 프로젝트 · 설계/개발/검증/배포 · [GitHub](https://github.com/answndud/kinderp) · [서비스](https://kinderp.cloud)

원장·교사·학부모가 사용하는 유치원 운영 시스템입니다. 커뮤니티 서비스와 달리 조직·사용자·원생·업무 상태가 강하게 연결되는 내부 제품으로 설계하고, MySQL·Redis·Spring Boot 기반으로 실제 운영 가능한 흐름을 구현했습니다.

### 구현과 설계

- 회원·유치원·반·원생·보호자 관계를 모델링하고, 요청자의 역할뿐 아니라 유치원 소속과 resource ownership을 함께 검사했습니다.
- 입학 신청의 신청·승인·제안·수락·거절·대기열 상태를 명시적인 상태 전이로 만들고, 각 전이의 허용 actor와 audit 기록을 분리했습니다.
- 출결 기록·출결 변경 요청·인수인계를 transaction 단위로 묶어 학부모 요청과 교사 업무 처리가 서로의 상태를 덮어쓰지 않도록 했습니다.
- 공지·알림·알림 Outbox를 분리하고 delivery status·retry·dead-letter 흐름을 만들어 외부 알림 실패를 운영자가 확인할 수 있게 했습니다.
- 인증 세션·refresh rotation·rate limit·auth audit log를 추가해 내부 운영 시스템의 계정 lifecycle과 이상 징후를 추적했습니다.
- Testcontainers 기반 MySQL·Redis 통합 검증, Docker health check, GHCR image pull, 공용 Caddy를 구성했습니다.
- TownPet과 하나의 netcup VPS에서 80/443 포트 충돌 없이 실행되도록 내부 Caddy·`edge` network·컨테이너 memory limit을 설계했습니다.
- MySQL dump·checksum·disposable restore와 이전 이미지 기동 후 현재 이미지 복귀 rehearsal로 배포 복구 절차를 확인했습니다.

### 이 프로젝트에서 배운 점

단순 CRUD에서는 드러나지 않던 tenant 경계, 상태 전이, 운영자 권한, 알림 실패를 먼저 모델링해야 내부 업무 시스템이 안전해진다는 점을 경험했습니다. 기능을 늘리기보다 누가 어떤 상태를 언제 바꿀 수 있는지와 실패 후 재처리 방법을 먼저 정의했습니다.
