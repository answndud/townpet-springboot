## 대표 프로젝트 — TownPet Spring Boot

### 반려동물 커뮤니티 플랫폼 재작성

2026 · 개인 프로젝트 · 설계/개발/성능 측정/배포 전 과정

기존 TownPet의 화면과 사용자 흐름을 유지하면서 backend를 Java/Spring Boot 기반 modular monolith로 재작성한 반려동물 커뮤니티입니다. 게시글·댓글·좋아요·북마크·알림·신고·입양·봉사·돌봄·미디어 업로드를 제공하며 React/Vite frontend와 직접 연결했습니다.

#### 주요 기여

- Spring Boot Controller·Request/Response DTO·Validation과 React API client를 직접 연결해 외부 계약을 단순하게 유지
- PostgreSQL·PostGIS를 source of truth로 두고 Flyway migration, JPA, transaction 경계를 설계
- Spring Security·Spring Session JDBC·CSRF·RBAC·resource ownership으로 회원·운영자·비회원의 접근 경계를 분리
- 게시글 수정·댓글·북마크·신고·미디어 첨부에서 URL의 사용자 식별자를 권한 근거로 사용하지 않고 session principal과 소유권을 함께 검사
- 공개 피드에 `(created_at, id)` 기반 keyset cursor와 복합 index를 적용해 삽입 중 페이지 중복·누락 가능성을 줄임
- 작성자 게시글 공개범위 일괄 변경을 JPA entity 전체 로딩에서 조건부 PostgreSQL bulk update로 변경하고, 실제 변경 row만 version·updatedAt을 갱신
- 조회수 경로를 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` atomic upsert로 변경해 동시 요청의 lost update를 방지
- 봉사 수용 인원·미디어 첨부·돌봄 수락처럼 공유 불변식을 깨뜨릴 수 있는 mutation에만 row lock을 적용
- Event Publication Registry와 PostgreSQL 기반 후속 이벤트 처리에서 consumer idempotency와 retry 경계를 유지
- Docker Compose·공용 Caddy·PostgreSQL/PostGIS·MinIO·GHCR 구조로 실제 VPS에 배포하고, KinderP와 하나의 VPS를 공유하도록 내부 네트워크와 외부 포트를 분리

#### 검증 가능한 결과

- 100,000건 publication fixture에서 public feed index 전후 p95를 `67.13ms → 5.01ms`로 측정
- 조회수 동시 요청 160건을 8개 thread로 실행해 최종 counter와 요청 수를 대사
- capacity contention에서 정원 불변식은 유지됐고, row lock 비용은 application p95 약 `238.98ms`로 별도 기록
- 대표 public feed 최신 3회 측정에서 p95 `4.35~6.40ms`, 오류 0을 확인
- PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`와 deterministic fixture로 인덱스·정렬·상한 query를 검증
- PostgreSQL·MinIO paired backup과 KinderP MySQL backup을 생성하고 checksum·disposable restore·age 암호화 복호화를 확인

#### 설계 판단

- 처음부터 Redis·Kafka를 추가하지 않고 query plan·DB contention·event backlog를 먼저 측정했습니다. 현재 병목과 eventual consistency 요구가 입증되지 않아 복잡도를 늘리는 도입은 보류했습니다.
- 모든 조회에 무제한 결과를 허용하지 않고 feed cursor, 목록 상한, 안정적인 정렬 기준을 적용했습니다.
- JPA bulk update는 entity lifecycle callback이 필요하지 않은 moderation 경로에만 사용하고, 일반 도메인 변경은 entity·transaction 경로를 유지했습니다.
