## 프로젝트

### TownPet Spring Boot — 반려동물 커뮤니티 플랫폼

2026 · 개인 프로젝트 · 설계/개발/검증/배포 · [GitHub](https://github.com/answndud/townpet-springboot) · [서비스](https://townpet.cloud)

기존 TownPet의 화면과 사용자 흐름을 유지하면서 backend를 Java/Spring Boot modular monolith로 재작성했습니다. 게시글·댓글·좋아요·북마크·알림·신고·입양·봉사·돌봄·미디어 업로드를 React/Vite frontend와 연결했습니다.

- PostgreSQL/PostGIS를 source of truth로 두고 Flyway migration, JPA, transaction 경계를 설계했습니다.
- Spring Security·Spring Session JDBC·CSRF·RBAC·resource ownership으로 회원·운영자·비회원의 접근 경계를 분리했습니다.
- 공개 피드에 `(created_at, id)` keyset cursor와 복합 index를 적용해 삽입 중 페이지 중복·누락을 줄였습니다.
- 작성자 게시글 공개범위 일괄 변경을 entity 전체 로딩에서 조건부 PostgreSQL bulk update로 바꾸고, 실제 변경 row만 version·updatedAt을 갱신했습니다.
- 조회수를 PostgreSQL atomic upsert로 변경해 동시에 160개 요청을 처리해도 lost update가 발생하지 않도록 했습니다.
- 봉사 수용 인원·미디어 첨부·돌봄 수락에는 공유 불변식을 보호하는 row lock을 적용하고, 후속 알림은 Event Publication Registry와 idempotent consumer로 분리했습니다.
- Docker Compose·공용 Caddy·GHCR·MinIO 구조로 KinderP와 하나의 VPS에 공동 배포하고 backup/restore·image rollback을 rehearsal했습니다.

**측정 결과**

- 동일한 local Docker/PostgreSQL fixture에서 100,000건 publication의 public feed p95 `67.13ms → 5.01ms`
- 동일 환경의 public feed 최신 3회 측정 p95 `4.35~6.40ms`, 오류 0
- capacity contention application p95 약 `238.98ms`; 정원 불변식 유지
- PostgreSQL `EXPLAIN (ANALYZE, BUFFERS)`, deterministic fixture, 160건 동시성 fixture로 query·정합성 검증

**핵심 판단**

Redis·Kafka를 먼저 추가하지 않고 query plan·DB contention·event backlog를 측정했습니다. 현재 병목 근거가 없어 cache invalidation·eventual consistency·운영 복잡도를 늘리는 도입은 보류했습니다.
