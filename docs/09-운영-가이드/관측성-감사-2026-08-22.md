# 관측성·운영 감사 2026-08-22

## 시나리오 재현: "15:17에 사용자 액션이 실패했다"

운영 환경에서 실패 요청을 실제로 발생시키고 운영자 관점에서 복구를 검증했다.

1. 클라이언트가 `X-Trace-Id` 없이 POST → 응답 ProblemDetail에 `traceId` 포함 (사용자가 제공 가능)
2. 운영자가 `docker logs | grep <traceId>`로 즉시 해당 요청의 method/path/status/duration 확인
3. 결과: **재구성 가능** ✓

## 감사 결과

### 강점 (유지)

| 항목 | 근거 |
|---|---|
| trace 상관관계 | RequestTraceFilter → MDC → 모든 로그 행, 응답 헤더로 사용자에게 반환 |
| 오류 로깅 | GlobalProblemHandler가 unhandled exception을 stacktrace와 함께 ERROR 기록, 클라이언트에는 고정 detail만 노출 |
| 민감정보 | password/token/credential 로깅 코드 0건 확인 |
| 지연 가시성 | 모든 HTTP 요청 duration_ms 기록 |
| 배포 진단 | healthcheck unhealthy 시 자동 image rollback, build version commit SHA 주입 |
| graceful shutdown | `server.shutdown=graceful`, 20s drain, restart unless-stopped |
| 백업 | paired backup 스크립트 + failure webhook + retention cron (03:45 매일) |
| 이벤트 회복 | Modulith PostgreSQL 영속 + 재시작 republication |

### 발견·조치 (`c526a21`)

| 문제 | 조치 | 효과 |
|---|---|---|
| 요청 로그에 query string 부재 — 검색·필터 실패 원인 파악 불가 | http_request 로그에 query 추가 | "어떤 검색어에서 실패했는지" 추적 가능 |
| Spring Security startup WARN 반복 출력 — 진짜 경고 묻힘 | 해당 logger를 ERROR level로 격상 | 로그 노이즈 감소 |

### 남은 한계 (수용)

- 로그가 docker stdout에만 존재해 컨테이너 재생성 시 유실. 단일 VPS sandbox 규모에서 외부 log shipper는 과도하다고 판단, 도입하지 않음
- metrics는 actuator health/info만 노출. 현재 트래픽에서 Prometheus 등 추가 인프라는 필요성 미확인
- backup 자체의 cron은 미등록 — 수동 실행 + prune cron 구조. 백업 자동화는 별도 운영 결정 사항으로 유지
