# 운영 관측성

특정 시각의 사용자 실패는 응답의 `X-Trace-Id`, backend 로그, 실행 중인 build version을
같이 조회한다. 로그에는 token·password·Authorization·session·recipient email·presigned
URL·raw query를 기록하지 않는다.

```bash
docker inspect --format '{{.State.Health.Status}}' townpet-backend
docker exec townpet-backend wget -qO- http://127.0.0.1:8080/actuator/health
docker exec townpet-backend wget -qO- http://127.0.0.1:8080/actuator/info
docker compose --env-file /opt/townpet/secrets/portfolio.env \
  -f deploy/compose/netcup.yml ps
docker compose --env-file /opt/townpet/secrets/portfolio.env \
  -f deploy/compose/netcup.yml logs --tail=200 backend
```

Actuator는 공용 frontend/Caddy 경로로 공개하지 않고 backend 컨테이너 내부에서 확인한다. 외부에서는 `townpet`·`erp` HTTPS smoke와 사용자 흐름을 별도로 확인한다.

## 요청과 오류

backend 요청 로그의 최소 field는 다음과 같다.

- `event=http_request`
- `trace_id`, `method`, 안전한 `path`, `status`, `duration_ms`, `build_version`
- query 원문 대신 `query_present`

인증 entry point, 권한 거부, rate limit, state conflict는 각각 event/category로 구분한다.
예상 가능한 4xx는 오류 원문이나 credential 없이 원인 category를 남기고, 예상하지 못한 5xx는
stack trace와 함께 `trace_id`로 조회한다.

조사 순서:

1. 사용자 응답의 `X-Trace-Id`와 실패 시각을 확보한다.
2. 해당 trace와 `build_version`의 `http_request`를 찾는다.
3. 같은 시각의 `security_rejected`, `request_rejected`, dependency event를 확인한다.
4. container 상태의 restart count·OOM 여부와 PostgreSQL/MinIO/backend 로그를 대조한다.

## 비동기와 예약 작업

계정 token delivery는 recipient나 raw token 대신 purpose, attempt, outcome, duration을
기록하고 Modulith event publication registry의 pending/completed 상태와 대조한다.
`retryable_failure`와 `exhausted`는 SMTP 장애 조사 신호다.

notification consumer는 `success`, `skipped_self`, `duplicate` outcome을 구분한다.
`duplicate`는 idempotent replay로 처리하되 data-integrity 원인을 로그에 남긴다.

`search_event_cleanup`은 매 실행마다 success/failure, deleted count, duration을 기록한다.
마지막 성공 시각이 오래되거나 failure가 반복되면 PostgreSQL 상태와 scheduler/container
재시작을 확인한다.

## 외부 의존성과 health

- readiness: DB를 포함한 application readiness를 확인한다.
- MinIO: Actuator health의 MinIO contributor와 operation latency를 확인한다.
- SMTP: account delivery의 retry/exhausted event와 mail health를 함께 확인한다.
- PostgreSQL: readiness, Hikari metrics, DB container health와 connection budget을 대조한다.

MinIO metrics는 operation/outcome만 label로 사용하며 object key나 URL을 label로 사용하지
않는다. 외부 장애의 원문 예외는 backend 로그 보존 정책 범위에서만 조회한다.

## 배포·재시작·rollback

`deploy/deploy-netcup.sh`는 `deployment_id`, phase, image/build version, health, restart/OOM,
rollback과 smoke 결과를 출력한다. 실패 시 TownPet의 postgres, minio, minio-init, backend,
web과 공용 edge 로그를 함께 수집한다.

```bash
docker inspect --format 'container={{.Name}} status={{.State.Status}} health={{if .State.Health}}{{.State.Health.Status}}{{else}}none{{end}} restart_count={{.RestartCount}} oom_killed={{.State.OOMKilled}}' townpet-backend townpet-postgres townpet-minio townpet-web
docker compose --env-file /opt/townpet/secrets/portfolio.env \
  -f deploy/compose/netcup.yml logs --tail=200 postgres minio minio-init backend web
docker compose --env-file /opt/edge/secrets/edge.env \
  -f deploy/compose/edge.yml logs --tail=100 edge
```

배포가 실패하면 migration 로그를 먼저 확인하고 web을 최신 backend에 연결하지 않는다.
rollback은 이전 backend image와 web image를 함께 복원하며, `SMOKE_URL`이 지정된 경우
외부 smoke도 다시 실행한다.

## Backup·restore·workload

backup, restore, retention, workload checker는 실행 ID를 포함한 `event=` line을 출력한다.

- backup: `backup_id`, phase, duration, manifest/checksum, failure alert 결과
- restore: PostgreSQL·MinIO 단계, row/object 대사, duration, failure phase
- retention: dry-run 여부, retention policy, removed count
- workload: DB connection·memory·storage 값, PASS/WARN/CRITICAL, alert 전달 결과

현재 저장소와 운영 기록으로 확인된 것은 paired backup/restore rehearsal, checksum,
non-empty media fixture, workload baseline과 임시 webhook test까지다. production failure
webhook, 실제 retention deletion, 외부 failure-domain 복사와 복원은 별도 운영 evidence 없이는
완료로 판정하지 않는다.

## 현재 확인 기준

- readiness가 DB를 포함해 `UP`
- 모든 HTTP 요청에 응답 `X-Trace-Id`, 동일한 `trace_id`, `build_version`, 처리시간이 존재
- token·password·Authorization·session·raw query string이 log에 없음
- account delivery의 retry/exhausted와 Modulith publication 상태가 연결됨
- 예약 작업의 마지막 성공·실패·처리량을 확인할 수 있음
- DB·SMTP·MinIO 장애를 dependency와 operation 단위로 구분할 수 있음
- backup manifest와 checksum 파일이 생성됨
- PostgreSQL·MinIO disk 사용량이 VPS 여유 공간을 침해하지 않음

## 제한

외부 collector, Sentry, Prometheus와 장기 retention, 분산 tracing은 실제 운영 신호와 비용을
확인한 뒤 별도 결정한다. 현재 로컬 저장소만으로는 production log retention, alert receiver의
실제 수신, 수신함 deliverability와 VPS 외부 failure domain을 증명할 수 없다.
